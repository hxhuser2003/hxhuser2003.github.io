Synopsis

Who it's for. The team needed a dashboard to monitor its production cluster: one that tracks network resource usage, forecasts how it will change, and alerts the RAN engineers, so they don't have to watch it all day.

What I built. An end-to-end service that collects telemetry, forecasts resource pressure, recommends scaling actions and integrates predictions with dashboards and alerts. It was an individual internship project with mentor guidance. I built every part, from the data pipeline and model training to the backend, dashboard and deployment.

Engineering

Two paths: training and serving

The system has a training path and a serving path. The training path takes the regularly pulled telemetry, cleans it, builds features and trains several candidate models. Each candidate lands in a staging folder first and never touches production directly; it is promoted only if it passes a six-gate evaluation against the current model.

On the serving side, a long-running process pulls live data, runs the forecasts and anomaly scores, and hands the results to a rule engine. The rule engine sorts the load into four states, from green to red, and gives a concrete scaling recommendation. A language model turns all of that into a plain-language explanation for Grafana, and when things get urgent, alerts push it out so no one has to keep watching the panel.

Build it with the people who use it

My users were the RAN engineers on the team, so I met with them to gather requirements and iterated on the design with their feedback.

Close to delivery, the dashboard still read like an ML tool. I set up meetings with a senior RAN engineer and with an engineer who had built a similar dashboard. I then replaced AI terms with words RAN engineers already use, kept a short explanation where a term had to stay, and added an info icon to every panel. I delivered on time and walked the team through the finished dashboard.

Pick a stack that fits a batch forecasting service

  • Data: Prometheus and the NVIDIA DCGM exporter collect GPU, CPU and RAN telemetry on OpenShift. The metrics store keeps only a short window, so a scheduled job archives snapshots as Parquet for training.
  • Models: XGBoost and N-HiTS for forecasting; Isolation Forest and an autoencoder for anomaly scores. I kept XGBoost because N-HiTS raised too many false scale-ups.
  • Serving: a long-running Flask service runs a forecast cycle on a schedule and exports results to Prometheus for a Grafana and React dashboard.
  • Delivery: Docker images deployed to OpenShift by GitLab CI on every push to main, replacing a manual build, push and apply routine.

Telemetry only updates every 15 minutes, so the goal was for every cycle to finish on time, not low request latency. I hadn't used most of these tools before the internship and learned them on the job.

Compare models fairly before promotion

I separated the training path from the serving path. Scheduled telemetry snapshots feed cleaning, normalization and feature engineering; trained candidates are evaluated before they can replace the deployed model.

A high-load validation window exposed a blind spot that the earlier benchmark had missed. I compared the candidate and deployed models on the same recent holdout, rather than comparing scores from different evaluation periods. That made the promotion decision reflect the conditions the system needed to handle.

The promotion workflow checks six concerns: severe misses, high-load detection, under-prediction, false scale-ups, forecast error and state agreement. Blocking checks and monitored diagnostics have distinct roles. Before replacement, the current model is backed up; any manual override is explicit and logged.

Keep the serving path useful during failures

Forecasts pass through a rule engine that calculates a concrete scaling recommendation. A language model turns that decision into readable text; if it times out, disconnects or returns an invalid response, a Jinja template renders the recommendation instead.

I exported forecasts and states as Prometheus metrics so Grafana and alerting could consume predictions through the existing monitoring interfaces. Long-term capacity planning is a separate calculation from short-term forecasting, and raw telemetry stays separate from prediction outputs.

A network interruption had been stalling the update cycle. I shortened connection timeouts and used a fail-fast retry policy, with a last-good-data cache to preserve an output path. Capture-and-replay runs recorded windows through the same serving code, making state transitions reproducible during demonstrations.

Test interfaces and validate data

Training features and live-window features have different implementations. I added consistency tests around those boundaries to catch training/serving skew, alongside unit and integration coverage for data handling, model selection and serving behavior.

I also added sanity checks for implausible telemetry values. Rejected rows are logged, and regression tests preserve the validation behavior. Deployment troubleshooting fed back into a repeatable workflow and handoff documentation rather than remaining a sequence of manual fixes.

The AI part

XGBoost provides forecasting, while anomaly scores supplement deterministic health checks. The language model has a narrow role: explaining a recommendation already chosen by the rule engine. Template fallback keeps that optional text-generation step outside the core decision logic.

Results & limits

  • Deployed as 4 services on Kubernetes/OpenShift.
  • Built 305 pytest unit and integration tests.
  • Reduced VPN-loss failure detection from 64 seconds to 4.2 seconds.

Evaluation was lab-based. Anomaly detection coverage on real incidents still required validation, so anomaly scores were treated as advisory alongside deterministic alerts.
